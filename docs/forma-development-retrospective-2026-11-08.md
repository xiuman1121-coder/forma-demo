# Forma 开发复盘：从原型到公开可访问的求职 Demo

更新日期：2026-11-08。本文依据项目代码、Git 记录、已有研发文档，以及开发期间检查过的真实任务 Trace 整理。它记录**已观察到的事实**，并明确区分已修复的问题、仍需人工验证的质量问题和仅有推测的问题。早期 README 中的“本地、无登录、无真实模型”描述属于当时版本，不代表现在的线上版本。

## 一、我们做的产品是什么

Forma 面向需要制作电商商品视觉、但不想逐张从零构思和写生图指令的人。用户上传产品或参考图片，说出“帮我做一套电商主图”，系统把需求和素材放进同一个项目，规划每张图的用途与视觉方向，调用图像模型制作，保存在画布中，并支持后续对话修改、版本和导出。

产品要解决的核心问题不是“生成一张 AI 图片”，而是**从产品素材和模糊需求走到一套可继续修改的商品视觉**。面试时可以突出三点：一套图的规划、自然语言迭代、项目内连续保存。当前它是可供外部打开并实际体验的 Demo，尚不具备自动判断图片审美、产品保真或文案准确性的能力。

## 二、从开始到现在，经历了哪些阶段

| 阶段 | 原本的问题或目标 | 做过的事 | 当前结论 |
| --- | --- | --- | --- |
| 早期界面原型 | 需要把单纯表单变成创作工作台 | 做了 Chat、画布、素材、方向、作品和版本；初期使用预置素材与本地规则 | 验证了基本交互，但当时不是完整的真实 Agent 产品 |
| 接入真实模型 | 用户要真实理解图片和生图 | 接入智谱 Planning/执行 Agent 与火山 Seedream；密钥留在后端 | 可以真实生成，但模型限流、参数错误和供应商失败开始暴露 |
| 任务可靠性 | “说了要做图却没做”、数量错、工具错、上下文串项目 | 增加路由与执行权限、计划校验、任务上下文、Trace、单轮预算门禁 | 对技术性错误有更多拦截与可追溯记录；语义判断仍可能出错 |
| 多图与反馈 | 一套图需要逐张交付，并允许修改已有图 | 计划项、作品版本、失败保留、继续未完成项、最多两张独立图并发 | 可以部分交付；并发只缩短可并行的等待，不能保证每轮都快 |
| 公网求职 Demo | 面试官需要从自己的网络打开，且不能任意使用付费 API | 固定账号登录、无注册、香港轻量服务器、HTTPS、GitHub 版本管理 | 网站已公开可达，但只有知道共享账号的人能进入；所有人共用一个工作区和 API 账单 |
| 近期性能优化 | 生图、上传、项目封面加载慢 | 执行 Agent 改 low、二进制上传、封面图片私有缓存与按需加载 | 部分环节已明显缩短；网络和第三方模型耗时仍有波动 |

## 三、实际遇到的问题、原因与处理

### 1. 真实模型与图像接口最初无法稳定跑通

早期出现过智谱免费模型拥堵或 429、火山体验额度限制或 429、火山请求参数不符合接口要求、执行 Agent 工具参数缺项等情况。我们没有把“模型说会生图”当作成功，而是逐步做到：调用前检查参数和预算、模型不可用时使用已配置的备用路径、只有图像文件实际保存后才计入交付。真实生成、反馈改图和 PNG 导出后来均完成过端到端验证。供应商仍可能限流或拒绝请求，这类故障不可能由本地代码彻底消除。

### 2. 项目和上下文曾经串在一起

早期首页新任务、旧项目和参考图的边界不清，发生过红色边柜的对话和作品进入水杯项目。后来将项目数据隔离：新创作有独立项目，切换项目恢复各自的聊天、上传和作品；当前新上传的产品不应继承旧项目图片。误写的数据做了分离，但**修正记录不能改变当时已经受错误上下文影响的生成图片**。多轮任务还增加了素材来源、设计修订、确认状态与历史视觉参考的记录，避免“按刚才方案”只凭最近一条消息猜。

### 3. Planning 会把“做图”误判为“先写方案”

真实 Case 中，同一句“做一套电商主图”有时进入生图，有时进入草案。根因是 Planning 规则中“做一套图”和“做一套图方案”的边界不够清楚，而程序会执行模型返回的 `draft` 或 `generate`。后来修改的是 Planning 判定说明，让明确要图片的表达优先走制作；保留了用户明确要方案时只写方案的能力。用户当时不希望增加依赖正则的后端冲突判断，因此没有加入那种语义拦截。**这降低了已知歧义，不代表所有自然语言意图都能 100% 判对。**

### 4. Planning 偶尔输出无法解析的 JSON

系统提示词要求只输出 JSON，但一次真实任务中模型在字段后多写了 `,""`，导致解析失败。程序检测到错误后重新请求，第二次返回合法 JSON，任务继续完成。这里的问题是格式字符错误，不是那次任务的用户意图错误；提示词是软约束，不能保证每个字符都正确。当前采用解析、验证和有限重试的办法；重试会增加时间和一次模型请求成本。不能仅凭这一例断定 `low` 推理级别造成格式错误。

### 5. 路由、工具和交付数量曾不匹配

“把九宫格切成九张”曾被误解成“生成九张新图”；风格延展曾出现用户要两张而计划三张；边柜风格延展的计划和生图指令保留了原场景，导致结果像轻微改动。针对这些问题，项目增加了本地裁切工具、明确数量校验、风格延展中产品结构和新构图约束、计划项与实际交付的状态记录。Linux 部署后的裁切能力也做了适配。技术检查能确认文件、数量、来源与版本，**不能确认图像质量、文字是否正确或产品是否走样**。

### 6. 图片失败时，界面曾说不清具体原因

火山 HTTP 400 不能笼统等同于版权拒绝。它可能是输入、参数、策略等不同原因；需要看响应体和请求阶段。曾有一张图失败而其他图已保存，早期记录不足以把底层原因讲清。后来增加了 Seedream 传输错误的非敏感记录，以及逐张 Trace、文件存在性检查和部分交付状态。现在可以定位“哪张失败、在哪个环节失败、供应商返回了什么可安全记录的信息”；仍需对具体失败逐案查看 Trace，不能只看 HTTP 状态码猜原因。

### 7. 多图制作慢，单张执行 Agent 也慢

原链路是 Planning 决定一套图的方向，执行 Agent 再逐张整理生图工具参数，火山逐张生成。一个四张水杯图的旧任务总计约 3 分 53 秒：Planning 约 13 秒，逐张执行 Agent 约 57–69 秒，火山约 35–49 秒。只改 Planning 提示词无法直接消除执行 Agent 与火山等待。

为保留两层架构，我们先让**相互独立**的计划图最多两张并发；需要依赖上一张结果时保持串行。随后发现执行 Agent 使用智谱模型时没有显式设置推理强度，便将其设为 `low`。在一轮三张 T 恤主图中，执行 Agent 分别约 10.4、8.7、9.1 秒，火山分别约 18.0、18.0、18.8 秒；该轮 Planning 首次输出格式错误，21.0 秒后重试又用 19.8 秒，全轮约 96.2 秒。这个例子说明执行阶段比旧样本快，但任务内容、模型状态和网络都不同，**不能把所有提速都归因于 `low` 或并发**。并发也不意味着总时间必然减半。

### 8. 火山生图有时十几秒，有时四五十秒

我们曾怀疑“并发导致火山变慢”，但不能从几轮任务直接得出因果。曾在服务器上直接请求火山做小样本对照：单次约 41–64 秒，同时两次约 40–48 秒；另有真实任务约 18 秒。主要等待发生在供应商返回响应前，响应体处理只占很少时间。由此只能确认**供应商耗时存在较大波动**，不能证明是并发、图片内容或某个单一参数造成。现在保留分段 Trace，后续需要更多同条件样本才能作稳定判断。

### 9. 用户上传参考图慢

原先浏览器把图片转换为 Base64，再与预览图放进 JSON 上传，增加传输体积。后来改成二进制上传：原图字节直接发送，同时保留给模型理解使用的小预览图；原图仍按 8 MB 上限保存。改动已通过自动测试并上线。但上传还包括**浏览器解码、制作预览图、用户网络上行、服务器保存**，多张图片目前逐张上传。此前服务端日志未记录精确请求耗时，浏览器也未分别计时，因此不能声称“改后每张少了多少秒”；用户仍感到慢是合理反馈，下一步应补分段计时再优化瓶颈。

### 10. 项目列表的封面图出现得慢

列表直接引用作品原图，部分图片接近 6 MB；服务还要求每次重新下载。2026-10-31 的修改给登录后的图片添加浏览器私有缓存，并让项目列表按需加载可见封面。这会改善重复访问和长列表首屏；**首次打开仍可能下载大原图**。若首次访问体验仍差，应该在服务器端为项目封面生成真正的小尺寸缩略图，而不是只依赖缓存。

### 11. 公网登录、费用和部署边界

为了让面试官打开网站，同时限制付费 API 被随意调用，选择了**一个固定账号和密码、没有开放注册**。密码不以明文写进 GitHub；配置脚本将密码哈希与会话密钥写入服务器私有配置。未登录请求不能读取项目、API 或图片。服务器在腾讯云香港轻量实例上运行 Node 服务，由 Nginx 提供 HTTPS，应用本身只监听本机。GitHub 保存代码，线上服务器保存运行数据与密钥，更新代码需要重新部署。

当前所有知道共享账号的人进入**同一个工作区**，看到同一批项目、素材和对话；他们的模型调用使用服务器配置的智谱与火山 API Key，因此供应商实际费用由这些 Key 对应的账号承担。应用内人民币 80 元是本项目自己的预算/预留上限，**不是智谱或火山后台的真实余额、账单或硬性扣费上限**。正式多用户产品需要独立身份、数据隔离、额度与访问控制；求职 Demo 目前没有做这套体系。

### 12. 稳定性与回归测试

开发中出现过“服务重启后任务中断”“图片已保存但后续步骤失败”“失败后仍显示部分作品”等边界情形。现在任务记录区分完成、部分完成和失败；对已经保存的图片检查文件存在，失败后保留已交付作品，不自动无限重试付费生图。Debug Trace 可在排障时开启，按任务 ID 记录 Planning、Agent、工具、Seedream 和文件检查；Trace 可能包含用户需求或商业素材名，不能公开。自动测试主要用 Mock 供应商验证路由、预算、项目隔离、上传、改图、版本、裁切和交付状态；它们**不能代替真实模型质量测试或外部网络实测**。

## 四、现在实际达到了什么

- 可以从外网通过 HTTPS 打开，并用固定账号登录；没有注册入口。
- 能在项目中上传素材、聊天、规划和制作多张图；作品保存到画布，可继续按自然语言修改和导出。
- Planning 与逐张执行 Agent 的职责保留；独立图片可最多两张同时执行。
- 有应用内预算、逐张状态、失败保留、有限重试与排障 Trace。
- 代码已放在 GitHub；线上运行与私有数据在服务器，二者需要在每次正式更新时同步。

这些是**功能和技术交付状态**，不等于“每张图都好看、商品完全保真、文字绝对正确、任何网络下都快”。

## 五、仍然存在的限制和下一步优先级

1. **先把体验测清楚。** 为浏览器图片预处理、上传、列表封面加载补精确计时；用实际用户网络重复测试。生成任务继续按 Planning、每张执行 Agent、每次火山请求和保存拆分耗时。
2. **优化首次图片加载。** 生成项目封面专用缩略图，避免首次列表加载大原图。缓存已解决重复下载的一部分问题。
3. **做真实回归，而不只看自动测试。** 至少覆盖新建项目、上传、三到四张图、局部失败、继续未完成项、修改指定作品、版本、导出、刷新和重新登录；记录视觉质量和费用。
4. **明确视觉质量的人审边界。** 当前系统不会自动验收产品保真、商标文字、排版和创意差异；面试 Demo 应直说需要人工检查。若要进一步自动化，应先定义可测的质量标准和成本上限。
5. **完善对外介绍。** 首页应让面试官快速看懂目标用户、痛点和一个完整用例；目前产品价值表达弱于功能展示。
6. **后续正式产品再考虑多用户。** 共享账号适合受控演示，不适合公开注册和彼此独立使用。

## 六、可用于面试的简短讲法

> 我做了一个电商视觉创作 Demo。用户上传产品图，说一句“做一套主图”，系统先规划每张图的用途，再逐张生成，并允许在同一个项目里继续修改和导出。我把它从本地原型部署成了可登录的 HTTPS 网站。开发中真正难的不是接一个生图 API，而是让系统正确理解“讨论方案、直接生图、修改已有图、裁切原图”的区别，保证多张图的状态、预算、部分失败和项目上下文不会乱。后来我用真实任务 Trace 找到耗时分布，再针对执行 Agent、并发、上传和图片加载逐项优化。现在它能完成真实流程，但视觉质量仍需要人工验收，供应商耗时也有波动。
