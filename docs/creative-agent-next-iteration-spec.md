# Forma Creative Agent 下一轮研发与验收规格

状态：部分实施，仍有待验收项。基线：2026-10-09 的本地 Forma。本文供实现和验收时逐项核对；不能把“写入本文”视为功能已完成。

## 实施记录（2026-10-09）

- 已实现：九宫格请求在协调器中走 macOS 本地 `sips` 裁切，九张文件各自成为画布作品，记录来源与行列；旧的误规划切图计划禁止继续付费执行。裁切仅支持规则 3×3 等分，尚无格线/留白自动检测；非 macOS 会明确失败。
- 已实现：明确数量与规划数量不符时，在任何生图调用前失败；风格延展需要结构化色彩、光线、氛围与逐张不同的新构图，否则停止。计划与实际生图 Prompt 仍由现有 GLM 负责，质量遵循需人工实测。
- 已实现：无明确文字要求的计划项不提供 `edit_text`；旧文字层保留。风格分析可在交付计划展开查看。生成结果若与参考图或已有作品文件完全相同，会标为人工复核，但近似复刻、产品失真和排版错误仍无法自动识别。
- 已实现：画布内 `Ctrl/Command + 滚轮` 与触控板捏合更新局部倍率，普通滚动不拦截。尚需目标设备手测不同浏览器的捏合手势和缩放锚点。
- 自动化：`npm run check` 与 Mock/本地测试通过；没有调用真实付费模型。真实视觉效果和供应商模型遵循尚未验收。

### 边柜风格延展回归（用户 2026-10-09 截图）

真实审计显示：规划把原客厅、左侧植物、右侧沙发保留，只要求机位“略微偏右”和道具“微调”；第一张实际生图 Prompt 重复这些元素，只用“红色格栅边柜”描述产品，遗漏开放层、双门等关键结构。第二张仍要求沙发和植物，成品近似去字版。根因不是“需要更长的 Prompt”，而是结构化计划虽存在，却没有检查产品身份和画面差异；Agent 自由生成的 Prompt 又把坏计划传给图像模型。

针对这一真实 Case，调用前门禁新增产品可见结构、原场景、新场景、新机位和新构图字段；“微调/略偏右/同场景”会拒绝，规划器最多修正一次，仍不合格则停止且不调用付费生图。风格延展生图 Prompt 从已验证的计划确定性组装，明确保留产品结构并排除原场景复刻。无文字任务在图片保存后立即结束本计划项，避免额外的无效工具调用。Mock 回归已覆盖“坏计划被拒绝→修正→实际 Prompt 保留结构”的路径；真实 Seedream 对产品外观的遵循和近似复刻识别仍需要有限人工验收，不能宣称已彻底解决。

## 0. 产品目标与成功定义

Forma 服务电商主图、详情图和品牌视觉创作。它需要理解用户的交付意图，选正确的操作，规划彼此有区别的作品，使用真实工具，检查交付，并允许用户继续修改。目标不是把任意用户话术改写成一条生图 Prompt。

本轮成功的最低标准：

1. 对“裁切、修改已有作品、参考素材生成新作品、纯分析、排版、画布导航”作出不同处理；不能全部流向 `create_image`。
2. 用户说“两张”就规划两张；用户说“原图切九张”就交付九个由原图裁出的文件。明确数量不得被规划器擅自增加。
3. 参考图的视觉风格与参考图的内容/构图分离。新图可以共享风格与真实产品身份，但不能把换掉一两个道具当作创意延展完成。
4. 只有文件存在、数量正确且来源关系正确，才标记技术交付；视觉质量、产品保真、文案与排版要单独验收。
5. 所有自动化测试使用 Mock/本地图片，不调用付费 GLM 备用或 Seedream；保留现有 ¥10 总预算、¥0.80 单任务上限和不无限重试的原则。

## 1. 已确认的现状与失败证据

### 1.1 实际链路

`server.mjs /api/run` 保存用户文本与显式选中的素材 → `backend/task.mjs requestPlan` 把项目摘要、选中图片传给 GLM-4.6V-Flash → `parsePlan` 得出 `conversation/generate/edit` 和图片列表 → `runTask` 逐项交给 `backend/agent.mjs runAgent` → Agent 让 GLM 选择工具、参数 → `create_image/edit_image` 调 Seedream 5.0 Flash → 作品版本写入项目 → 前端 `dist/studio.js` 展示与导出。

当前可用工具仅有 `save_brief`、`create_image`、`edit_image`、`edit_text`、`restore_version`（`backend/agent.mjs:10-16`）。没有裁切/切片工具、结构化风格分析产物、版式生成器或视觉质量检查工具。

当前计划项仅保存 `purpose/sellingPoint/visualDirection/referenceIds/targetAssetId`（`backend/task.mjs:35`）。图像任务上下文把用户原话和本张用途拼成一段话（`backend/task.mjs:87`），实际生图 Prompt 再由 GLM 自由写入工具参数。交付检查只确认文件和数量；`quality` 是 `not_evaluated`（`backend/task.mjs:14-17, 94-109`）。不要把完成状态解释为设计质量合格。

### 1.2 真实失败 Case 与可验证结论

| Case | 用户实际目标 | 当前记录 | 失败定位 |
| --- | --- | --- | --- |
| 九宫格切片 | 将一张现有九宫格原样切成九个独立图片 | 计划被解释为九种电商图片用途；实际调用三次 `create_image`，Seedream Prompt 写成“3x3 网格布局”；留下六项待执行 | 规划/操作路由错误 + 无裁切工具；不应继续该旧计划，否则可能继续付费生图 |
| 浴室暖色视觉延展 | 先分析视觉特征，再基于风格创作两张不同画面 | 计划写了三张，实际保存两张；计划含“暖色调、柔和光影、极简”，但没有规定新构图须与原图不同；成品沿用原图瓶子、台面、毛巾等关系 | 数量校验缺失 + 风格和内容未分离 + 无相似性验收 |
| 作品上的黑体文字 | 像设计成品一样组织字体与画面 | `edit_text` 只支持文本、坐标、字号、颜色；前端以单层半粗系统字体叠加，导出固定 `PingFang SC`（`dist/studio.js:16-18`） | 排版工具/数据模型不足；“可编辑”不等于“已设计” |
| 画布缩放 | 在画布范围内用触控板/鼠标缩放，页面其他区域不缩放 | 现有按钮只更改 `#canvas` CSS transform；没有画布范围内的触控板捏合处理（`dist/studio.js` 的 `zoom`） | 局部 UI 输入事件问题，与 Agent 质量问题分开处理 |

上述记录来自当前项目与受限审计文件；审计记录不应被复制进公开前端或测试快照。不能凭截图断言 Seedream 一定无法做创意延展：前面的任务与 Prompt 已经错了，先修上游再评估模型。

## 2. 根因判断与范围

首要根因是 Agent harness/编排过粗，不是用户 Prompt 写得不够详细。

- **任务分类太粗**：`generate/edit/conversation` 无法表达“对已有像素作确定性裁切”“仅分析”“参考风格新建”“排版”。`explicitIntent` 使用关键词提示，LLM 计划未受操作能力清单约束。
- **工具集不完整**：没有裁切工具时，系统仍允许把“切图”送进付费生图，结果必然偏离目标。工具缺口不能靠增加系统提示词解决。
- **创意规划信息不足**：没有独立的 `styleAnalysis`、`preserve`、`avoidCopying`、每张的 `novelComposition`、`contentDifference`、`copyPolicy` 等可检查字段。原始参考图直接进入 Seedream，容易把布局也一起带过去。
- **图像 Prompt 缺少编排契约**：当前允许 GLM 自由生成 Prompt，没有检查它是否与计划项对应、是否要求复制九宫格、是否违反无字约束、是否重复上一张构图。
- **交付检查只管文件**：没有生成后视觉检查，更没有“发现近似复刻 → 受控修改一次 → 仍不合格则报告”的闭环。视觉评估需要定义准确的失败类型和预算界限，不能简单相信模型一句“已完成”。
- **排版能力不够**：单文字层只支持基本位置和颜色，缺少层级、字体、字重、字距、对齐、留白、安全区域、遮挡检查。现在自动加字会伤害成品质量。
- **模型能力是待验证的次级变量**：GLM-4.6V-Flash 和 Seedream 5.0 Flash 可能在意图理解、风格抽象、图像遵循上有局限；但在正确路由、工具、计划和检查建立前，换模型无法解释或修复以上确定性错误。本轮不迁移模型。

“Skill”在本项目里应是可执行的设计方法与工具使用规则，例如九宫格切图或电商主图约束；不是先建设一个复杂 Skill 平台，也不是只写一段长 Prompt。

## 3. 推荐的最小目标架构

在现有 `server.mjs → task.mjs → agent.mjs → 画布` 上增量扩展，保持旧项目兼容：

```text
用户文字/选中素材/项目上下文
  → Intent Contract（任务类型、目标、数量、是否允许付费、歧义）
  → 路由
      crop_grid → 确定性本地图像切片工具 → 9 个关联原图的文件
      analyze_style → 结构化风格分析 → 回复/供后续任务引用
      style_extend → 风格分析 → 差异化作品计划 → 逐张 create_image
      generate/edit → 保留现有图像工具与版本关系
      typography → 文字需求判断 → 可编辑版式或明确暂不自动加字
  → 技术检查（文件、尺寸、数量、来源、版本、费用）
  → 视觉检查（产品身份、风格一致、与原图及同批作品的差异、文字遮挡）
  → completed / partial / failed / needs_input；记录检查依据
```

确定性需求优先走确定性工具。LLM 负责理解模糊需求和有判断空间的创意规划；协调器负责校验和安全边界。不能让 LLM 虚构一个工具，也不能让工具成功替代质量验收。

## 4. 分阶段实施规格

### P0-A：操作路由和九宫格切片

目标：明确“切成九张”是原图像素操作，不是九张新设计。先限定规则 3×3 网格；格线不清、存在不等宽/留白时要求确认裁切区域，不能猜测且不能退化为生图。

实现边界：

- 扩展任务契约，至少区分 `conversation`, `analyze_style`, `generate`, `edit`, `crop_grid`, `typography`；不要仅靠一个包含“切”字的正则，需结合选中素材和输出描述。明确目标资产/上传图 ID 与目标数量。
- 为 `crop_grid` 增加本地裁切工具：解码原图，按验证后的 3 列 3 行边界输出九个图片；文件必须分别可读、有非零尺寸、按左上至右下排序，并标明 `sourceId`、`row`、`column`、原图尺寸与裁切矩形。图像处理库选择以本地可用性与测试可重复性为准；不引入大型服务。
- 切片不消耗 Seedream 预算，也不受“单任务 4 次图像模型调用”限制。新增作品与裁切来源关联，保留原图；旧项目显示保持不变。
- 对以前误规划的“九宫格九张创作图”待执行项加防误执行检查。用户点击“继续未完成图片”时不能沿旧计划继续付费；提示重新选择“裁切原图”或“创作九张新图”。现有已生成文件保留，不删除。

验收：Mock/本地 fixture 输入一张 3×3 色块图 → 得到九个不同的像素区域，位置、顺序、尺寸正确；Seedream 调用计数为 0；原图及旧作品不变；歧义格线不触发付费请求。

### P0-B：数量、任务类型和调用前校验

目标：防止“两张计划三张”“切片误用生图”“图像工具与操作类型不匹配”。

- 从用户明确数量提取 `requestedCount` 并与 LLM 计划比较；不确定时向用户询问，不能暗自增加。多图上限只决定本轮执行数量，不减少完整计划。
- 每个计划项增加 `operation`, `deliverableType`, `sourceIds`, `targetAssetId`, `expectedOutputCount` 和可检查约束。迁移采用可选字段及默认值，不强制改写旧 JSON。
- 协调器在任何付费调用前检查操作类型、目标绑定、参考图来源、预算、任务数量和已完成作品。失败原因记录为 `planning_error`/`routing_error`/`tool_error`，不要用一句“图片生成失败”覆盖。
- 不允许 `crop_grid` 调 `create_image`；不允许 `analyze_style` 直接调付费生图；不允许仅有上传参考图时假装已选画布作品。

验收：对用户原句进行参数化 Mock 回归；同一句话在有/无画布作品、有上传图、多张图时均选择正确路径；明确“两张”只规划两张。

### P1-A：风格分析 → 差异化创意延展

目标：把“沿着原图风格延展”转成可检查的中间产物，而不是把参考图原样送给生图模型。

风格分析至少输出：`palette`（色彩）、`lighting`（光线）、`materials`（材质）、`mood`（情绪）、`compositionTraits`（可借鉴的构图语言）、`productFacts`（仅可观察/用户提供的事实）、`mustPreserve`、`mustChange`、`uncertainties`。区分“品牌产品身份必须保留”和“原照片的手、毛巾、灯、台面摆放不应照抄”。分析应可在工作台被用户看见或展开，不应只藏在 Prompt 中。

每张延展作品必须另有：用途、场景、主体景别、视角、构图、道具、留白、与原图不同之处、与本批其他作品不同之处、是否需要文字。给生成模型的 Prompt 从这些结构化字段组装；允许 LLM 提议，但协调器检查缺项、重复和相互矛盾。保留参考图时明确它的角色是 `style` 还是 `product`，避免全图构图被错误当成必须保留。

对截图 Case 的参考分析示例（供验收，不硬编码为所有浴室图）：米色/暖棕、暖色柔光、简洁干净的浴室材质、日常护理仪式、克制治愈。两张新图应保留上述视觉关系，但分别采用不同的场景/景别/拍摄视角；不能只移走手、毛巾或灯。不要臆造产品功效或品牌文案。

验收分两层：

1. Mock：风格分析有完整字段；两张计划在场景和构图上有实质区别，数量正确；给 Seedream 的两个 Prompt 不只是换标题；无外部资料时不编造卖点。
2. 有限真实人工验收：用户看原图及两张新图，判断风格是否延续、内容是否明显不同、产品是否保真。若无法可靠自动判断，标记 `quality_review_required`，绝不自动声称“设计质量合格”。

### P1-B：受控的视觉检查与修改闭环

目标：技术成功不再掩盖“复刻原图、产品失真、错误文字、遮挡”。第一版只覆盖几类高价值错误，不建复杂 Evaluator 平台。

- 生图后检查文件可读及尺寸；在独立评估结果中记录 `product_identity`, `style_match`, `novelty_vs_reference`, `difference_within_set`, `text_integrity`, `composition`，并记录证据与不确定性。
- 可先以规则检查明显错误（数量、尺寸、重复文件 hash、计划间相同 Prompt）。视觉判断如调用 GLM 图像理解，必须有独立预算、可关闭开关与 Mock 测试；不把 GLM 评价当成绝对真理。
- 自动修复最多一次，且必须得到具体错误类型、指定原作品/参考图与修复约束。预算不足或问题不确定时停在 `quality_review_required`，让用户决定。不能无限重试，也不能把旧错误结果删掉。
- 结果报告分 `technicalStatus` 和 `qualityStatus`；截图中的“文件与数量已检查 · 视觉质量待验收”必须与数据一致。

验收：Mock 输入“近似原图”→ 被识别/标为待复核而非质量通过；一次受控修复后仍失败 → 停止并保留两版；工具失败和模型评分失败不会触发额外付费生图。

### P1-C：默认文字层停止冒充设计成品

目标：不再自动把黑体/系统字压在产品上。现有文字层和旧版本继续可编辑、可导出。

- 对每张计划增加 `copyPolicy: none | editable_overlay | designed_layout`。没有明确文字需求的产品细节图/场景图默认 `none`；标题只写在作品卡片标题，不写进图片。
- 当用户确实要求电商文案时，先定义文字内容、层级、对齐、位置安全区、字体组合与对比关系，再渲染到可编辑层。不要让当前仅含 x/y/size/color 的单文字层自动承担“设计排版”。
- 排版能力不足时，明确只交付无字图片和待排版计划，不用系统字糊弄成品；不允许文字遮挡产品核心区域。
- 后续可增多个可编辑文字层和有限版式模板，但本轮不要为此引入完整设计编辑器。

验收：同一张产品图生成无字细节图时 `layer.text` 为空；明确需要文案时有可读的层级和避让；导出与画布预览一致；旧项目的已有文字层不被清除。

### P2：画布范围内的触控板/鼠标缩放

这是独立 UI 交互项，不要混进 Agent 工具或图像质量改造。

- 指针在 `#viewport` 内时，触控板捏合（通常是带 `ctrlKey` 的 wheel）和约定的鼠标缩放手势只改变 `#canvas` 倍率；以指针位置为缩放锚点，调整容器滚动使该点保持稳定。
- 右上角按钮与百分比显示同步；最小/最大倍率有边界；普通滚动与拖动画布不被误判为缩放；聊天区、侧边栏和输入框事件不被拦截。
- 浏览器/操作系统手势存在差异；必须在目标桌面环境手测触控板双指、鼠标滚轮、滚动条、文字输入与页面缩放行为。

验收：在画布内缩放时只有作品变大变小；聊天区与侧栏尺寸不变；放大前指向的作品仍留在视野中；按钮与触控板混用后百分比正确。

## 5. 数据、状态与审计约束

- 保存每项计划的版本、操作类型、来源 ID、目标 ID、预期数量、实际工具、参数摘要、产物文件、版本、技术与质量状态、失败代码。已完成作品在重新规划时保留。
- 实际发给图像模型的 Prompt 只保存在 `.private/audit/<jobId>.json`，文件 0600、目录 0700；API Key、Authorization、图片 base64 不进入审计、前端状态或测试快照。审核日志必须能回答“为什么选此工具”“为何出 3 张而非 2 张”“是否真的发送了生图请求”。
- 作品的 source 关系必须区分上传产品图、风格参考图、构图参考图、旧作品、裁切来源及上一版本。不能再只靠最新作品推断目标。
- `completed` 仅表示承诺的技术交付完成；`qualityStatus=not_evaluated/review_required/passed/failed` 独立。不要把模型文字“已完成”当成工具执行证据。
- 保留 `.private/project.json`、`budget.json`、所有原始上传与作品版本。测试全部使用临时数据目录。对已有错误计划采取阻断/重规划，不自动删除或重复收费。

## 6. 实施顺序、验证门槛与停止条件

1. 先为四个真实 Case 建固定回归 fixture 与断言，检查项目历史兼容。特别固定“切九张 ≠ 生九张”“两张 ≠ 三张”。
2. 先做 P0-A/P0-B：任务路由与确定性裁切。全量 `npm test`、语法检查、Mock 端到端通过后才碰下阶段。
3. 再做 P1-A：风格分析和差异化计划。先验证结构化中间结果与 Prompt，不以真实生图效果替代计划测试。
4. 再做 P1-B/P1-C：视觉质量状态与文字策略。真实图像验收限定少量用户明确批准的调用；记录调用次数、预留费用和供应商实际账单的不确定性。
5. P2 画布手势独立开发与 UI 手测，避免改变图片/任务数据。

任一阶段出现以下情况立即停止自动执行并报告：任务类型不确定；目标图不明确；计划数量违反用户明确数量；缺少所需确定性工具；预算将超限；模型要求不存在的工具；图像请求成功但产物不可读；评估无法给出可靠结论；自动修复达到一次上限。不得用“继续生成”绕过这些停止条件。

## 7. 研发结束时必须交付的证据

- 文件级改动清单，说明每个新字段/工具与旧数据兼容策略。
- 全量自动测试结果和新增 Case 的逐项结果；注明是否使用任何真实付费 API。
- 对九宫格 Case 展示九个切片文件及零生图请求证明；对风格 Case 展示风格分析、两张有差别的计划和最终图片的质量状态；对文字 Case 展示无字默认策略与旧文字层兼容；对缩放 Case 展示目标桌面环境手测记录。
- 未解决问题按“任务理解、工具、图像模型遵循、质量评估、UI”归类，不用笼统的“模型效果不佳”代替定位。

## 8. 非目标

不更换 GLM/Seedream；不做多 Agent 架构、完整 Skill 平台、大型排版编辑器、无限画布重写、自动无限修复；不把用户现有项目迁移到新数据文件或删除错误作品；不通过付费 API 跑自动测试。
